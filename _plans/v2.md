# Neo v2 — migration and cleanup plan

Status: draft, 2026-10-31. Source: Notion "Neo personal v2 redesign plan" (same date). This file covers **how to get from what is live today to that architecture**, and what to clean up first. Nothing here has been executed.

## 1. Review of the Notion plan

The direction holds: deterministic policy engine + outbox for anything critical, eve for the chat and proactive layer, endpoint agents unchanged. These points in the note are wrong or missing, and would have caused trouble in M0:

1. **Neo is live, not pre-alpha.** Phases 1–3 and deferred-roadmap steps 1–4 are merged and running on www.neoshield.dev, with migrations 0001–0015 applied to Neon and real enrolled devices. v2 must be **additive on the live schema** (rename via views and backfills, no drop and recreate). Migration 0016 is taken by PR #50 (Outlook); the next free number depends on what happens to #50.
2. **Vercel Root Directory is `apps/web`.** The note puts `agent/` next to `apps/web` under Vercel Services. That needs either Root Directory moved to the repo root (and a Services config), or eve placed inside `apps/web`. This is a deploy-config change that affects production, so the M0 spike has to decide it. The root `vercel.json` (last touched in #12) differs from `apps/web/vercel.json` and Vercel reads only the latter, so the root one is stale or a seed for a Services config. **Decided:** stale, deleted (eve is Next-hosted, no Services).
3. **Inngest does more than cron.** Seven functions: `weekly-digest`, `devices-offline` and `breach-monitoring` (cron), plus `signal-escalate`, `alert-created`, `email-received` and `artifacts-expire` (event-driven). The note only covers cron and `signal-escalate`. Proposed new homes:
   | Inngest function | v2 home |
   | --- | --- |
   | `weekly-digest`, `devices-offline`, `breach-monitoring` | eve schedules |
   | `signal-escalate` | policy engine, run inline on ingest, writes the incident and outbox row |
   | `alert-created` (owner email) | outbox row, drained by an eve schedule |
   | `email-received` (Resend inbound) | keep the webhook route; it calls the analyzer directly or opens an eve session |
   | `artifacts-expire` | retention schedule (also covers the signal TTL from §6 of the note) |
4. **`docs/contracts.md` changes come first.** The desktop and extension clients ship signed builds, so contract changes need to be backward compatible and written down before code:
   - heartbeat response gains `policy_version` and a policy-bundle URL (old clients ignore the new fields)
   - a new `GET /api/devices/policy` (device token, ETag, signed bundle)
   - `member_id` resolved server-side from the device (never sent by the client)
   - incident, action and child-request APIs for the console and eve tools
5. **eve is not in the repo yet.** The M0 spike is a go/no-go gate, not a formality. It must prove:
   - eve 1.0.0-rc.1 builds alongside Next 16 + Turborepo + pnpm (`minimumReleaseAge` and the Tauri exclusions apply)
   - eve's route auth can reuse the Auth.js session and `getSession()` (including `neo_dt_` desktop tokens), and every eve tool goes through `tenantScoped()`
   - the trust-boundary envelope (`wrapToolResult`) can wrap eve tool results
   - the model can be pinned to the routed Claude models through AI Gateway (keeping the Haiku 4.5 rules: no `thinking` or `effort`)
   - the rc pin is acceptable: sessions started on one eve version strand after an upgrade outside Vercel Workflow. If GA is near, wait for it.
6. **`apps/web/vercel.json` `functions`** pins `maxDuration` for `/api/agent`, `/api/agent/confirm` and `/api/inngest`, all of which v2 removes. Update it in the same PR as each removal (the 300 s default makes the entries redundant anyway).
7. **Cost of SMS.** Twilio needs A2P 10DLC registration (weeks of lead time). If SMS is the critical channel (open question 2), start registration in M0.

## 2. Phases

Each phase is its own `_specs/` file, branch and PR, following the existing workflow. Phase order follows the note's milestones (M0–M4), with the migration work threaded through.

### M0 — Cleanup and groundwork
1. Cleanup in §3 (CI and Dependabot first, so the rest has green builds).
2. Answer the open questions in the note (§8 there). Questions 2, 3 and 5 block M1 scope.
3. Spec `_specs/v2-architecture.md`: deploy layout (decision from §1.2), contract changes (§1.4), and the Inngest mapping (§1.3).
4. eve spike on a branch with a preview deployment: one web chat via `useEveAgent` that calls `analyze_url`, authenticated by the existing session and tenant-scoped. Go/no-go against §1.5. **GO 2026-10-31**, locally and on a Vercel preview (Next.js-hosted, Root Directory and build command unchanged; see the spec).
5. Update `CLAUDE.md` (layout, rules for eve tools) and `docs/contracts.md`.

### M1 — Elder MVP (strangler, old chat still live)
- Migration: `members` (backfill one per existing user, role from household role), `modes`, `policies`, `incidents`, `actions`, `notification_outbox`, `consents`; add `member_id` to `devices`. All RLS'd and granted to `app_user` as existing migrations do.
- Policy engine in `packages/core` (pure TS, unit-tested): the 5 rules from the note. It replaces `signal-escalate`; existing `scam_in_progress` correlation moves into it.
- Outbox + drain schedule; email (Resend) first, SMS when Twilio is ready. Critical alerts are templated.
- eve agent with read-only tools first (`get_incident`, `device_timeline`, `analyze_url/email/sms`), then acting tools with `always()` approval.
- Admin console pages: members, modes, notify rules. Chat page moves to eve behind a flag; `/api/agent` stays until parity.

### M2 — Child MVP
- Policy bundle signing (minisign key separate from the release key) and `GET /api/devices/policy`.
- Extension: category filtering with declarativeNetRequest, SafeSearch; new extension release.
- Desktop: app blocklist and install approval, screen time; new signed MSI/pkg (auto-update path already exists).
- Child requests flow.

### M3 — Cutover and proactive polish
- Move digest, offline sweep, breach checks and retention to eve schedules. Run them **in parallel with Inngest for one cycle**, compare, then remove the Inngest functions, `/api/inngest`, the `inngest` dependency, the integration and its env vars.
- Remove `packages/core`'s agent loop, `/api/agent*`, NDJSON streaming and their `vercel.json` entries once the eve chat has parity (paste-a-link, playbooks, verdict cards).
- Agent memory, Twilio voice, end-session action.

### M4 — Hardening and release
As in the note: retention jobs, consent flow, privacy page, `SECURITY.md` threat-model update (new trust boundaries: eve tools, policy bundles, Twilio), evals, beta households.

## 4. Risks
- **eve rc.** If the spike fails any §1.5 check, fall back to AI SDK 7 + Workflow (`WorkflowAgent`) for durability, keeping the rest of the plan.
- **Signed client releases.** Any client-visible contract break strands installed agents; contracts stay backward compatible until the update path has rolled out.
- **Policy as an attack surface.** A compromised server could push a policy that disables protection. Bundle signing (M2) plus "alert all admins when a mode is turned off" (note §6) cover this; the signing key must not live in Vercel env.
- **Minors' data.** COPPA scope depends on open question 3; if it's only Patrick's household, keep the consent flow light but present.
