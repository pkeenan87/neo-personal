# Spec: Outlook.com connector

Branch: `hermes/feature/outlook-connector`
Roadmap: `_plans/deferred-roadmap-items.md`, step 5 (depends on step 4). Documentation-only; no implementation or migration is included.

## Summary

A read-only Microsoft Graph connector for a member’s personal Outlook.com mailbox. It audits inbox forwarding rules and discovers candidate security-alert messages for step 4. It is not a Neo sign-in provider and does not read Microsoft sign-in logs. It never sends, creates, changes, or deletes mailbox messages, rules, or settings. Work/school accounts are out of scope.

For alert filtering and analysis, use step 4’s `SIGNIN_ALERT_SENDERS` and `_specs/signin-alerts.md` only. Connector messages are passed through normal `analyzeEmail`, then the sign-in-alert path defined in that spec. Store parsed events only in the step-4 table. Do not duplicate the parser, fake-alert rules, event contract, or parsed-event table here.

## Microsoft API and OAuth

Use Microsoft identity platform v2.0 `/consumers` authority only and authorization-code flow with PKCE `S256`. Use delegated scopes only: `offline_access`, `User.Read`, `Mail.Read`, and `MailboxSettings.Read` (plus protocol scopes required for OAuth). The connector does not authenticate a Neo session.

`POST /api/connectors/outlook/start` and `GET /api/connectors/outlook/callback` require `requireBrowserApiSession`; a desktop bearer token is insufficient. Start creates a cryptographically random, single-use state transaction with a 10-minute TTL, bound to the initiating session user and tenant and carrying the PKCE verifier. Store only a hash of `state`; encrypt the verifier with `deriveKey(masterKey, "neo-connector-oauth-state-v1", tenantId)` and AAD `outlook-state:v1:<tenantId>:<userId>:<stateId>`, because it is a secret needed later to redeem the authorization code. Validate state, expiry, session ownership, and single use before exchanging the code, then consume the row. Redirect URI comes only from `OUTLOOK_REDIRECT_URI`; there is no `returnTo` parameter. Handle `access_denied` without echoing `error_description`. The callback is covered by the fake Graph/OAuth client in `MOCK_MODE`.

- On callback, use Graph `/me` to bind the stable account id and a display address; the address is not an account key. Never log or return access/refresh tokens, authorization codes, PKCE material, or opaque delta URLs. `OUTLOOK_CLIENT_ID`, `OUTLOOK_CLIENT_SECRET`, and `OUTLOOK_REDIRECT_URI` are optional environment variables listed in `.env.example`; when any is unset the feature is off.

### Token protection and refresh

- Encrypt access and refresh tokens with authenticated encryption using `deriveKey(masterKey, "neo-connector-v1", tenantId)`; these bearer credentials grant mailbox access if the database is disclosed. Bind ciphertext with AAD exactly `outlook:v1:<tenantId>:<userId>:<connectorId>`. The connector is disabled when `NEO_MASTER_KEY` is unset; never persist plaintext.

Persist `token_version` with the credential row. Refresh uses compare-and-swap on that version. If another refresh wins, reread the row and use the newer token rather than overwriting it. On `invalid_grant`, set `reauth_required`, pause polling, and do not retry-loop. Encrypt delta cursors separately with `deriveKey(masterKey, "neo-connector-cursor-v1", tenantId)` and AAD `outlook-cursor:v1:<tenantId>:<userId>:<connectorId>`, because the opaque Graph delta URL is sensitive mailbox state and may contain continuation material. Never log plaintext credentials or cursors.

## Inbox rule audit

On connect and daily thereafter, read inbox rules with `GET /me/mailFolders/inbox/messageRules`, selecting only fields needed to inspect enabled status, rule id/name, and `forwardTo`, `redirectTo`, and `forwardAsAttachmentTo`. Classify rules as disabled, internal-only, external-forwarding, or indeterminate. For outlook.com accounts, any destination address that is not the user’s own address is external. The own addresses are Graph `mail` and `userPrincipalName` only (`otherMails` is user-editable contact data and is never requested or trusted), compared case-insensitively with `+tag` removed on Microsoft consumer domains. A destination is never unwrapped: a value that is not a plain `local@domain` address (a display-name wrapper, `<…>`, a list) is *indeterminate* and handled as external, so it alerts. Normalize for comparison; retain only concise rule evidence and destination domain, never the full destination address or rule JSON.

An enabled external or indeterminate forwarding rule raises the new `mailbox_forwarding` high alert, with the member as `subject_user_id`. Alert text identifies an enabled inbox rule forwarding/redirecting mail to an external destination and gives the destination domain only. The owner view shows connected status, last check time, and the forwarding alert; the owner sees the destination domain only, not an address. Repeated findings are deduplicated; the finding row carries `alerted_at`, set only after the alert succeeded (or was skipped by policy, e.g. an owner's own mailbox, or already existed through the dedupe key), and every audit re-raises active findings with `alerted_at IS NULL`, so a transient alert failure is retried by the next audit without duplicating it; disabling/removing a rule resolves the active finding while findings and alerts follow existing retention. Implementation adds `mailbox_forwarding` to `ALERT_KINDS`, drops and re-adds `alerts_kind_check` in the migration, adds its template in `apps/web/lib/server/alerts/templates.ts`, and mirrors it in `memory-alerts.ts`.

`MailboxSettings.Read` does not expose account-level SMTP forwarding in documented Graph v1.0 mailbox settings. UI and privacy copy must say that Neo audits inbox rules only and cannot verify account-level forwarding.

## Bounded message delta and step-4 handoff

Poll Inbox every 15 minutes through Inngest. Use the opaque Graph delta `nextLink`/`deltaLink` as sensitive state. Each page request uses `$select` without body fields and `Prefer: odata.maxpagesize=50`; process no more than 10 pages per run. Persist the latest `nextLink` after each page so work is bounded and resumable. Never log cursor URLs. A failed page must not advance beyond the last durably processed cursor. Every cursor and poll/audit-time write is fenced on `status = 'connected'` and the `connection_generation` read when the run started (bumped on connect, reconnect, disconnect and `reauth_required`, not on token refresh), so a poll in flight across a disconnect or reconnect writes nothing back and ends `skipped`. A delta reset (410) drops the cursor and still records `last_poll_at`.

For each delta run, preserve this order: (1) request a delta page using a limited `$select` with no body fields; (2) prefilter candidates against step 4’s exported `SIGNIN_ALERT_SENDERS` (provider → exact sender addresses/domains); (3) for each candidate, GET `internetMessageHeaders` plus the body required by normal `analyzeEmail`; (4) treat authentication as passing only when the shared `auth.ts` analysis reports `dkim=pass` on a DKIM domain allowlisted for that provider. The `From` header is attacker-controlled; inspect `Authentication-Results` from `internetMessageHeaders`. Connector-sourced messages go through normal `analyzeEmail`, then the step-4 sign-in-alert path; step 4 owns classification, authentication decisions, verdict precedence, and event parsing. Store parsed events only in step 4’s table. Do not create a connector-owned parsed-events table.

A message that matches an alert format but has no authentication pass is stored in step 4's `signin_events` table with `source: "outlook"` and `authenticated: false`; it never produces a member verdict and therefore never reaches `alertForVerdict` or raises a `high` alert. Step 4’s deterministic policy controls authenticated candidates. The connector does not infer trust from `From` or implement provider templates. The first run establishes a 30-day baseline and raises no alerts for baseline messages. For Graph 429 responses, honor `Retry-After`, capped at one hour, through an Inngest sleep. Bound retries for other transient errors, and do not register Graph subscriptions/webhooks. Concurrency is per tenant (3) and one run at a time per connector (`event.data.connectorId`), for poll and audit. Idempotency across runs: `outlook_seen_messages` stores `message_key` = hex HMAC-SHA256 of the Graph message id under `deriveKey(masterKey, "neo-connector-msgid-v1", tenantId)` (dev key only when not deployed); a candidate's key is inserted-if-absent before processing and the message is skipped when it already existed, so a message re-emitted by a later delta run creates no second event, verdict or alert. A transient Graph failure releases the claim so the retry still processes the message. The daily audit purges keys older than 45 days; disconnect deletes them. **Mail links are never fetched**: candidates go through `analyzeEmail` with `maxUrls: 0` (no `analyzeUrl` fetch, DNS lookup or reputation query); step 4's link rules read `link_summary` hosts, which are extracted without network access.

## Disconnect, visibility, and privacy

`DELETE /api/connectors/outlook` requires a browser session and same-origin request validation. It disables scheduled work immediately, deletes local token ciphertext and delta cursors, and removes connector-local state. It links the member to `https://account.microsoft.com/privacy/app-access` to remove Neo’s Microsoft access. Findings and alerts remain according to existing alert retention. Do not call `revokeSignInSessions` or imply that Neo revoked Microsoft consent.

Every connection, token, cursor, rule finding, and event is tenant/user scoped and accessed through `tenantScoped()`. Members see their own connection and data. Owners see connected status, last check time, and resulting forwarding alerts only; no mailbox contents or event list. Do not store Graph message bodies. Existing step-4 event retention applies to parsed events.

Privacy copy must state the four delegated scopes; that Neo reads inbox rule metadata and polls Inbox; that only sender-allowlisted candidates have bounded message content fetched for analysis; what connection/rule/alert data persists and its existing retention; that a keyed fingerprint of processed message ids is kept for 45 days to avoid duplicates; that links in mail are never visited; that messages are not changed or sent; that account-level forwarding is not audited; and how to disconnect locally and remove Microsoft access through the account privacy page.

## Storage and migration

Connector records store tenant/user ownership, stable Microsoft account id, display label, status, `token_version`, `connection_generation`, encrypted credentials, encrypted delta cursor, last audit/poll timestamps, rule findings (with `alerted_at`), and `outlook_seen_messages` (tenant_id, connector_id, message_key, seen_at; PK (connector_id, message_key); composite FK to the connector, cascade). The short-lived OAuth state row stores only a state hash and encrypted PKCE verifier and expires after 10 minutes. OAuth states, connectors, and findings cascade on tenant/user deletion; findings also reference their connector within the same tenant. State the migration number is the **next free number at implementation time**. Every new table is tenant-scoped, registered in `tenantTables`, has `tenant_isolation` RLS and an explicit `app_user` grant (or note default privileges). No connector table stores parsed events; those belong only to step 4. No migration files or schema are created in this docs-only task.

## Acceptance criteria

- Personal Microsoft accounts only; `/consumers`; read-only scopes; PKCE S256; 10-minute, single-use, session-user-bound state; env redirect URI only, no `returnTo`; safe `access_denied` handling.
- Connector disabled when configuration or master key is unset; token encryption uses distinct HKDF label and exact AAD; `token_version` CAS rereads on conflict; `invalid_grant` becomes `reauth_required` without a loop.
- Delta requests omit body in `$select`, request page size 50, process at most 10 pages per run, persist `nextLink` after each page, establish 30-day no-alert baseline, and sleep on 429 using `Retry-After` capped at one hour.
- Prefetch uses step 4’s `SIGNIN_ALERT_SENDERS`; candidates go through normal `analyzeEmail` and step-4 sign-in path; only the step-4 table stores parsed events. No duplicate parser/event contract or connector event table.
- `From` is untrusted; `Authentication-Results` is read from `internetMessageHeaders`; unauthenticated alert-format messages are recorded only and never raise a high alert alone.
- New alert kind is `mailbox_forwarding`, member is subject, text is specified, owner sees destination domain only. For outlook.com accounts any non-own address/alias is external.
- Disconnect performs same-origin check, deletes local token/cursor state, links to Microsoft privacy/app-access, and leaves findings/alerts to existing retention.
- Privacy paragraph and owner view match the limits above; mock Graph covers OAuth callback; no live Graph access is needed for tests.

## Owner decisions adopted

Personal accounts only; owner registers the Microsoft app and client secret, with secret-expiry reminder in `CHECKLIST.md`; publisher verification is an owner decision before launch and is not a spec blocker; destination domain appears in owner alert; unauthenticated alert-format messages are recorded without alert; first poll uses a 30-day baseline. All credentials remain unset in repository documentation.
